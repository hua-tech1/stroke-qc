# 1. 定位与边界

## 1.1 一句话

面向急性缺血性卒中绿色通道，用 AI 识别 DSA 术中器械、自动生成客观时间戳，把「术中事件 → 超时预警 → 随访 → 质控整改」串成一条可审计的闭环。

## 1.2 三个失控点（立项理由）

| 失控点 | 现状 | 系统怎么解 |
| :--- | :--- | :--- |
| 术中器械时刻 | 靠口述、事后回忆补录 | 检测 → 滞回状态机 → 客观时间戳 |
| 术后随访 | 人工台账，凭记忆打电话 | 计划驱动 + 到期提醒 + 失访管理 |
| 质控上报 | 月末手工汇总，口径不一 | 过程留痕 + 自动算指标 + 整改闭环 |

## 1.3 对外定位（一句话，用于 PPT 第二页）

> **别人做的是"把病历里的数据抓出来上报"，我们做的是"把手术台上没被记录的那一段变成数据"。**

## 1.4 三层时间尺度（回答"为什么必须秒级"）

| 层 | 尺度 | 谁在用 | 秒级是否必需 |
| :--- | :--- | :--- | :--- |
| 事件层 | 秒 | 系统（检测、预警） | **必需** |
| 过程层 | 分 | 医生（判断、瓶颈） | 有用 |
| 指标层 | 月 | 质控科（上报） | 无增益 |

病例 A 的器械事件持续 **7.2 秒**；60 秒采样采到它的概率约 12%，漏 88%。不是测不准，是压根没有。

**答辩口径**：我们做秒级不是为了把 DNT 算得更准（它本来就是分钟级），是因为器械事件本身只有几秒，分钟级采样下它根本不存在。

## 1.5 明确不做（8 条）

1. 不做病灶识别、不做诊断、不给治疗建议
2. 不替代 HIS / DSA 设备 / 影像归档
3. 不做院前急救调度、急救地图、区域协同
4. 不做医保、病案首页对接
5. 不做账号注册、找回密码、改密
6. 不做趋势折线（仅 12 个月数据，且非真实）
7. 不做移动端、语音播报、暗色模式、多语言
8. 不做 NLP 抓病历自动填报（那是单病种上报厂商的主场）

## 4.2 三个关键设计（建表时定下的）

**① 事件与节点同表**
`milestones` 一张表装 14 类节点，其中两个是自动检测的（`device_visible_start/end`），靠 `source` 区分来源。
理由：它们本来就是流程的一部分，分表会让"时间轴"要 join 两张表才能拼出来。

**② 双时间字段**
```sql
occurred_at  timestamptz   -- 真实时间（device_clock / wall_clock）
seq_ts_ms    bigint        -- 序列内偏移（sequence_index）
ts_source    text          -- 决定哪个有效
```
约束强制二者至少有一个非空，且与 `ts_source` 匹配。
理由：检测事件只有序列偏移，手工节点只有真实时间，两者必须共存。

**③ 唯一性按来源区分**
```sql
CREATE UNIQUE INDEX uq_ms_active ON milestones (case_id, code)
  WHERE voided = false AND source <> 'detector';
```
手工/接口节点同一病例只能一条有效；检测事件可重复（器械多次进出）。

## 4.2.1 真相源约定（实测后新增）

`cases` 上的 `arrival_at / ct_at / needle_at / puncture_at / reperfusion_at / discharge_at` 是**快照缓存**，
仅供列表页与快速查询；**指标一律读 `milestones`**。原因：

- 只有 `milestones` 带 `source` 与 `ts_source`，才能算「人工补录占比」、才能回答"这个时间谁录的"
- 两者由写入端双写，演示阶段由 `seed.py` 保证一致

**实测校验**：SQL 与 Python 两条独立路径算出的 DNT 中位数 / 达标率完全一致（52.1 / 66.7%），说明双写无偏差。

## 4.3 五条硬约束（写进 DDL 的）

| 约束 | 实现 |
| :--- | :--- |
| 排除必须说清类型 | `CHECK (exclude_reason IS NULL OR exclude_kind IS NOT NULL)` |
| 人工排除必须填说明 | `CHECK (exclude_kind <> 'manual' OR exclude_note IS NOT NULL)` |
| 只作废不删 | `CHECK (voided = false OR void_reason IS NOT NULL)` |
| 整改关闭必须带指标值 | `CHECK (status <> 'closed' OR metrics_at_close IS NOT NULL)` |
| 分母为 0 不许算率 | `CHECK (computable = false OR denominator > 0)` |

## 4.4 纳排视图

```sql
CREATE VIEW v_qc_eligible AS
SELECT * FROM cases
WHERE tenant='demo' AND case_type='ais' AND is_ihs=false AND exclude_reason IS NULL;
```
所有指标只认这个视图，查询时加 `WHERE period = $1`。

### 5.5.1 状态机（S8 已实现，`app/qc/findings.py`）

| 当前 | 可用动作 | 转到 | 前置条件（不满足直接 409） |
| :--- | :--- | :--- | :--- |
| open | 指派 | assigned | 责任人必须是 `users` 里启用的人，自动带期限（个案 7 天 / 系统性 30 天） |
| open | 驳回 | rejected | 必须写理由 |
| assigned | 开始整改 | fixing | — |
| assigned / fixing | 登记措施 | （不改状态） | 措施内容非空；closed/rejected 后不许再加 |
| assigned / fixing | 提交复核 | verifying | **至少 1 条措施记录** |
| verifying | 复核通过 | closed | **当期指标值由系统现场计算**，前端不传值 |
| verifying | 退回 | fixing | 必须写原因，`return_count + 1` |

三条规则为什么这么定：

1. **关闭值系统计算，不接受手填**。整改台账最容易变成"自己打个分说自己改好了"。
   `metric_value()` 现场跑指标引擎取当期值写入 `metrics_at_close`；数据库还有
   `qf_closed_needs_metrics` 兜底。
2. **无措施不许提交复核**。空转的整改不算整改，界面上按钮直接置灰，接口层也拦。
3. **退回次数本身是质量信号**。`return_count` 累积并显示在列表里——被退回两次的整改，
   说明措施是应付的。

所有迁移写 `audit_logs`（entity=`qc_finding`），详情页展示完整操作时间轴。

# 附录 A · 市场与定位（压缩）

市面四类：国家直报平台（合规上报）、卒中中心信息化（绿道打快）、单病种上报（NLP 抓病历）、专科随访。

**共同终点是"穿刺"**——穿刺之后的器械过程，没有系统在采。我们的位置就在这段黑箱。

答辩口径：
- "这不就是卒中中心系统？" → 那类到穿刺为止，之后靠护士回忆
- "单病种已经有 AI 了" → 他们 NLP 读病历，我们 CV 读影像
- "整改闭环很多系统都有" → 有模块不等于有闭环，大部分停在前半步
