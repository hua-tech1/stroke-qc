# 事件级保真（EFO）体系 · 落地清单（v2）

> 定位修正：**不是给华为写方案，而是通过比赛把华为的痛点亮出来，
> 并用我们后端/算法层做出来的东西，把痛点变成项目的亮点。**

---

## 0. 华为的痛点是什么（一句话亮出来）

**华为的量化/部署工具链，只验收"帧级"（mAP、吞吐、量化精度），不验收"事件级"；而华为的行业客户——质检、交通、安防——终端输出恰恰是"事件"。**

我们在自己的系统里证明：帧级验收会在数学上掩盖事件级的系统性损失。**我们不只是指出它，我们把"量化 + 校正 + 重标定"做出来，让评委看到这是一个被我们补上的能力缺口。**

---

## 1. 三大支柱 → 三个解法（关键：从"测量"升级到"解法"）

| 命题 | 痛点（亮出来） | 我们提供的解法（后端/算法层做实） |
|---|---|---|
| **P1 盲区** | 短于 133ms 的动作必然漏检 | 盲区自检 + **盲区感知参数建议**（按临床最短动作时长反推 k 上界） |
| **P2 放大** | 量化把帧级 5% 放大成事件级 16% | 量化对照 + **量化感知事件级重标定**（量化后自动重选 conf，把事件召回救回来） |
| **P3 偏置** | 时长固定偏长 +133ms | 偏置自检 + **偏置校正**（输出校正后的器械可见时长） |

**这三个"解法"就是亮点本身**：华为工具链验收不到这一层，而我们在系统里把它做成了可演示的能力。

## 5. 答辩怎么讲（亮痛点 + 亮解法，不写方案文档）

1. **痛点**：华为工具链只验收帧级，行业客户终端是事件——中间这层没人验收。
2. **我们做了什么**：在自己的卒中质控系统里，把这一层做成了**三条可证伪定律 + 三个解法**。
3. **演示**：术中监控页当场开量化仿真开关 → 评委看到"帧级没怎么降、事件级崩了" → 再点重标定 → 事件召回救回来。
4. **落点**：这不只是我们发现痛点，是我们在自己的系统里把"事件级验收"这个能力建起来了——华为看的是能力，不是建议书。

## 8. P3 偏置校正 · 详细实现

```
校正后滞留 = 原始滞留 − (m_out − k_in + 1) × Δt = 原始滞留 − 200 ms（k=3,m=5,15fps）
```

- 函数：`corrected_dwell(raw_ms, k_in, m_out, fps)`（纯函数，进 `event_audit.py`）
- 接入：术中监控滞留计时旁显示「原始 / 校正后」；PR08 校正值等事件落库（B9）后再作用到指标
- 验证：exp3 合成序列断言「校正后 == 真值」

## 9. P2 量化感知重标定 · 详细实现

- 问题：量化后 conf 分布漂移，原阈值 0.5 非事件级最优
- 算法：网格搜索 conf（0.30~0.70）→ 每个 conf 重跑 `generate_events` → 以 FP32 事件为参照算事件级 F1 → 取 F1 最大者 conf*
- 输出：baseline_f1(conf=0.5) / best_conf / best_f1 / gain
- 演示：量化后沿用 0.5 召回 0.84 → 重标定 conf*=0.43 恢复到 0.96
- 诚实标注：阈值重标定是旧方法，新意在"做成量化后的事件级恢复能力"
