# 多路并发接入管线 · 实现与实测

> 目标：把"昇腾 DVPP 多路"从架构图变成**可运行、可复现、有数字**的东西。

## 一、为什么这个实验能把 DVPP 创新坐实

一块边缘设备接管整个导管室，工程上由两部分组成：

| 部分 | 是否依赖昇腾硬件 | 现状 |
|---|---|---|
| **多路调度 / 批处理 / 保序 / 逐路事件化** | **不依赖**，与硬件无关 | ✅ 本目录已实现并实测 |
| 视频解码（DVPP VDEC） | 依赖 | 接口已预留；容量用官方规格推算 |

也就是说：这条管线 80% 的工程内容现在就已经存在、已经跑通、已经有数字。
DVPP 只是把"解码"这一格换成专用单元，管线的其余部分一行不改。

## 二、实现结构

```
每路 Producer（按 15fps 定时发帧 / 全速排空）
        │  写入有界队列（满则计为丢帧 → 背压）
        ▼
路间轮转调度器（每轮每路取 1 帧，凑满 batch 就发）
        ▼
单卡批处理推理（一次前向处理 N 帧）
        ▼
逐路状态机（packages/efo/generate_events，与系统同源）
        ▼
可选保序缓冲（按 frame_idx 重排后再喂状态机）
```

与 DVPP 的对应关系：

| 本实现 | 昇腾对应 | 说明 |
|---|---|---|
| `preload()` 预加载内存帧 | DVPP VDEC 硬解输出 YUV | 解码单元（本实验用内存帧替代，**未测 DVPP 吞吐**） |
| `Channel.produce()` 定时发帧 | 多路码流取帧回调 | 每路独立时钟 |
| 轮转调度 + batch | 同一 AI Core 上的推理调度 | 与硬件解耦 |
| `order_buffer` 保序 | 按 `frame_idx` 重排 | 多路异步回传的必备策略 |

> 昇腾上的解码接口有两种调用方式：`hi_mpi_vdec_*`（310 系列传统 DVPP 接口）与
> `aclvdec*` / `acldvpp*`（ACL 封装）。具体可用哪一个取决于目标 CANN 版本，
> 落地前需按目标板卡文档确认——本仓库**没有**在昇腾上验证过这一点。

## 三、实测结果

环境：RTX 5060 Laptop 8GB · ultralytics 8.4 · PyTorch 2.11+cu128 · imgsz 640 · 5 轮预热。
每路 80–90 帧，取自验证集 15 个序列（每路一个序列，帧间按 15fps 计时）。

### 3.1 纯推理容量（全速排空，含 Python 前处理与 NMS）

| batch | 单帧等效耗时 | 容量 | 可支撑路数 @15fps | 该路数下负载 |
|---:|---:|---:|---:|---:|
| 1 | 35.14 ms | 28.5 fps | 1.9 路 | 52.7% |
| 2 | 21.63 ms | 46.2 fps | 3.1 路 | 64.9% |
| 4 | **14.82 ms** | **67.5 fps** | **4.5 路** | **88.9%** |
| 8 | 13.13 ms | 76.2 fps | 5.1 路 | 157.6% |

**读法**：批处理把单帧等效耗时从 35.1 ms 压到 14.8 ms（batch 4），但 4 路时已到 **88.9% 负载**，
8 路直接超载（157.6%）。这组数字的结论不是"够用"，而是：

> **瓶颈不在解码，在推理栈本身。** 所以昇腾的价值不是"换个更快的芯片跑 YOLO"，
> 而是必须配合**模型固化 + 张量化推理**（ACL/ACLLite、静态 shape、去掉 Python 前处理），
> 否则多路必然饱和。这恰好解释了为什么通用方案进不了导管室。

### 3.2 实时多路时延（按 15fps 发帧，有保序）

| 路数 | 最差 p99（第 1 次） | 最差 p99（第 2 次） | 丢帧 | 事件与基准一致 |
|---:|---:|---:|---:|---:|
| 2 | 280.6 ms | 66.3 ms | 0 | 2/2（两次） |
| 4 | 159.9 ms | 432.2 ms | 0 | 4/4（两次） |

**读法**：**事件一致性是稳定的**（两次独立运行都是 4/4），
但 **p99 时延跨运行波动一个数量级**（4 路 159.9 → 432.2 ms），
原因是单次运行 + 笔记本 GPU 与他进程共享 + Python GC 抖动。

> **因此时延不作结论。** 材料里若要引用，只能写"数十至数百毫秒量级，未做重复测量"。
> 结论只落在两处：① 事件语义不受并发影响；② 4 路时通用推理栈已接近饱和（见 3.1）。

### 3.3 乱序注入（p=0.3，4 路，90 帧）— 最关键的一组

| 条件 | 第 1 次 | 第 2 次 | 结论 |
|---|---:|---:|---|
| 无保序缓冲 | **1 / 4** 正确 | **1 / 4** 正确 | 稳定复现 |
| 有保序缓冲 | **4 / 4** 正确 | **4 / 4** 正确 | 稳定复现 |

**读法**：多路异步回传一旦乱序，4 路里只有 1 路还能产出正确事件——
另外 3 路的事件序列被破坏（合并、拆分或错位）。加一个按 `frame_idx` 重排的缓冲，
**4 路全部恢复**。

这组数字**两次独立运行完全一致**，是本目录唯一可以当作结论引用的核心结果。
p99（345.0 / 88.3 / 187.3 / 1871.3 ms）同样波动剧烈，不作结论。

## 四、复现

```bash
# 容量（约 1 分钟）
python experiments/ascend_multichannel/pipeline.py --mode capacity --channels 1,2,4,8 --frames 80
# 实时时延与事件一致性（约 30 秒）
python experiments/ascend_multichannel/pipeline.py --mode realtime --channels 2,4 --frames 90 --buffer on
# 乱序：无保序 / 有保序
python experiments/ascend_multichannel/pipeline.py --mode realtime --channels 4 --frames 90 --reorder-p 0.3 --buffer off
python experiments/ascend_multichannel/pipeline.py --mode realtime --channels 4 --frames 90 --reorder-p 0.3 --buffer on
```
产物：`out/capacity.json`、`out/realtime.json`、`out/reorder.json`。

## 五、不能越过的边界

1. **没有在昇腾上跑过**：解码用内存帧替代，本实验不含 DVPP VDEC。
2. **本机时延不能搬成昇腾时延**：ultralytics Python 前端开销占大头，昇腾走 ACL 会不同。
3. **未做多次重复**：p99 为单次运行值，存在波动；p99 差异不作因果解释。
4. **乱序模型是相邻交换仿真**（p=0.3），不是 DVPP 实测乱序分布。
5. 帧率按 15fps 假设（数据集未提供采集帧率）。
6. 本实验**不证明**临床有效性，也不证明"一台设备接管整个导管室"——
   后者还需 DVPP 实测与固化推理的时延数据。
